# 2.3. Синхронные контракты и API

**Тезис главы:** синхронный API — это не просто набор URL и форматов JSON. Это договор между системами о том, как запросить действие или данные, что считать успешным результатом и как вести себя при ошибке.

## Теория и пример из кейса

### Что такое синхронное взаимодействие

При синхронном взаимодействии одна система отправляет запрос и ожидает ответ в рамках того же обмена:

1. Клиент вызывает API.
2. Сервер обрабатывает запрос.
3. Сервер возвращает результат или ошибку.
4. Клиент продолжает работу на основании ответа.

Например, сайт магазина запрашивает карточку товара у каталога. Пока каталог отвечает, сайт может показать страницу. Такой обмен удобно использовать, когда вызывающей системе нужен результат **сейчас**: получить данные, проверить доступность операции или подтвердить, что запрос принят.

Синхронное взаимодействие связывает участников по времени: вызывающая сторона зависит от доступности и скорости отвечающей. Поэтому проектируя API, архитектор должен продумать не только успешный сценарий, но и таймауты, повторы, частичные сбои и поведение при недоступности зависимости.

### Контракт — договор между потребителем и поставщиком

У API есть как минимум две стороны:

- **потребитель** отправляет запрос и использует результат;
- **поставщик** обрабатывает запрос и гарантирует определённое поведение.

Контракт описывает:

- назначение операции;
- адрес и HTTP-метод;
- параметры запроса и формат тела;
- обязательность и допустимые значения полей;
- формат ответа;
- ошибки и их смысл;
- правила авторизации;
- ограничения по времени, размеру и частоте запросов;
- правила совместимости и изменения API.

Например, контракт `GET /products/{id}` должен определить, что происходит, если товар найден, скрыт от продажи или не существует. Если ответы и ошибки не описаны, потребитель вынужден угадывать поведение поставщика.

### Ресурсы, операции и семантика HTTP

Для API интернет-магазина полезно моделировать предметную область через ресурсы: товары, заказы, остатки, пункты выдачи. URL обычно обозначает ресурс, а HTTP-метод — действие над ним.

| Метод | Типичное назначение | Пример |
|---|---|---|
| `GET` | Получить данные | `GET /products/sku-104` |
| `POST` | Создать ресурс или запустить операцию | `POST /orders` |
| `PUT` | Полностью заменить представление ресурса | `PUT /customers/42/address` |
| `PATCH` | Частично изменить ресурс | `PATCH /orders/845` |
| `DELETE` | Удалить или отменить ресурс, если это предусмотрено контрактом | `DELETE /carts/18/items/3` |

Метод должен соответствовать смыслу операции. Например, создание заказа обычно выполняют через `POST /orders`, а не через `GET`: чтение не должно неожиданно создавать заказ или менять состояние системы.

Нельзя полагаться только на код HTTP. Контракт должен объяснять и содержимое ответа. Например, `201 Created` означает, что ресурс создан; клиенту может понадобиться идентификатор созданного заказа и ссылка на него. `202 Accepted` уместен, если запрос принят, но работа ещё не завершена. Это важно различать: «заказ создан» и «запрос на создание заказа принят в обработку» — не одно и то же.

### Проектирование запроса и ответа

Представление API должно быть удобным для потребителя, но не раскрывать случайные детали внутренней реализации. Например, сервис оформления заказа не обязан возвращать внутренние таблицы базы данных или названия внутренних микросервисов.

Упрощённый запрос:

```http
POST /api/v1/orders
Content-Type: application/json
Idempotency-Key: 8f4a1c...
```

```json
{
  "customerId": "customer-42",
  "items": [
    {
      "sku": "sku-104",
      "quantity": 2
    }
  ],
  "delivery": {
    "method": "pickup",
    "pickupPointId": "spb-015"
  }
}
```

Возможный ответ:

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/v1/orders/order-845
```

```json
{
  "id": "order-845",
  "status": "created",
  "items": [
    {
      "sku": "sku-104",
      "quantity": 2
    }
  ],
  "total": {
    "amount": 6400,
    "currency": "RUB"
  }
}
```

Пример намеренно упрощён. В реальном контракте нужно определить, например, в каких единицах передаётся сумма, как округляются значения, какие поля обязательны и что происходит с неизвестными полями.

Не стоит включать в ответ поля «на всякий случай». Каждое поле становится частью договора: потребитель может начать от него зависеть, и удалить или изменить его будет сложнее.

### Ошибки: часть контракта, а не исключение

Клиенту важно понять, что произошло и можно ли исправить запрос. Практичное API различает ошибки по смыслу:

- **ошибка в запросе** — например, отсутствует обязательное поле;
- **отказ по бизнес-правилу** — например, товара не хватает для заказа;
- **отсутствующий ресурс** — например, неизвестный идентификатор;
- **ошибка аутентификации или авторизации**;
- **временная техническая ошибка** — например, зависимость недоступна.

Полезный ответ на ошибку содержит стабильный код и безопасное для клиента описание. Например:

```json
{
  "code": "INSUFFICIENT_STOCK",
  "message": "Недостаточно товара для выбранного количества",
  "details": {
    "sku": "sku-104",
    "requested": 2
  },
  "requestId": "req-73b1"
}
```

Клиент может показать человеку понятное сообщение, а по `code` выбрать предусмотренное поведение. Не следует возвращать наружу стек вызовов, SQL-запросы, секреты или подробности внутренней инфраструктуры.

### Таймауты, повторы и идемпотентность

Если ответа долго нет, клиент не может знать наверняка, завершил ли сервер операцию. Возможно, запрос не дошёл до сервера. Возможно, сервер создал заказ, но ответ потерялся. Если клиент бездумно повторит запрос, появятся дубли.

Для безопасного поведения проектируют:

- **таймауты** — максимальное время ожидания;
- **политику повторов** — какие ошибки можно повторять, сколько раз и с какой задержкой;
- **идемпотентность** — возможность повторно отправить запрос без нежелательных повторных эффектов.

Для создания заказа клиент может передать ключ идемпотентности. Поставщик сохраняет результат обработки ключа и при повторном запросе возвращает прежний результат, а не создаёт второй заказ. Контракт должен определить область действия ключа, срок его хранения и поведение при повторном использовании ключа с другим содержимым.

Повторять запросы следует осторожно. Повтор `GET` обычно безопаснее, чем повтор операции создания или оплаты. Даже технически повторяемый запрос может создать чрезмерную нагрузку, если все клиенты начнут повторять его одновременно. Помогают ограничение числа попыток, задержка между ними и случайное смещение задержки.

### Версионирование и совместимость

API развивается, но потребители могут обновляться не одновременно. Поэтому важно отличать изменения, которые обычно совместимы, от изменений, способных сломать клиентов.

Чаще всего менее рискованно:

- добавить необязательное поле в ответ;
- добавить новую операцию;
- добавить новый необязательный параметр, если его поведение определено.

Потенциально несовместимо:

- удалить поле;
- изменить тип или смысл поля;
- сделать необязательное поле обязательным;
- изменить формат ошибки;
- изменить правила авторизации или семантику операции.

Конкретная стратегия версионирования — например, версия в пути (`/v1`) — зависит от контекста. Но версия сама по себе не решает проблему: нужны правила поддержки старых потребителей, сроки вывода версии и процесс объявления изменений.

### Пример: оформление заказа в онлайн-магазине

В первой версии магазина сайт отправляет синхронный запрос в сервис заказов. Сервис проверяет данные, рассчитывает итоговую сумму и создаёт заказ. Сайт ждёт ответ, чтобы показать номер заказа и результат оформления.

До проектирования контракта команда должна ответить на вопросы:

- Что означает успешный ответ: заказ уже создан или запрос лишь поставлен в очередь?
- Когда резервируется товар?
- Что получит клиент, если товар закончился между отображением корзины и оформлением?
- Что делать сайту, если ответ не пришёл, а заказ мог быть создан?
- Можно ли повторить запрос? Как предотвратить дубли?
- Какие поля и ошибки нужны сайту, а какие — внутренние детали сервиса?
- Сколько времени сайт готов ждать ответа?

Позже магазин подключает службу доставки. При оформлении заказа сайт не должен обязательно ждать, пока внешняя служба окончательно оформит доставку: её API может быть медленным или временно недоступным. Синхронный контракт может отвечать за получение доступных способов доставки или расчёт предварительной стоимости, а создание отправления может происходить отдельным шагом. Выбор зависит от требований бизнеса: если оформление заказа должно завершаться даже при временной недоступности доставки, архитектуре нужно предусмотреть альтернативный поток, а не просто увеличить таймаут.

**Архитектурный вывод:** синхронный API подходит для запроса немедленного результата, но каждый такой вызов добавляет зависимость по доступности и времени ответа. Контракт должен заранее определить границы этой зависимости и поведение при сбоях.

## Проверка знаний

### Вопрос 1

Сайт повторно отправил запрос создания заказа: первый запрос мог успешно обработаться, но ответ потерялся. Какая характеристика контракта помогает избежать создания дубля?

- A. Использовать более подробное сообщение об ошибке
- B. Добавить ключ идемпотентности и определить его обработку
- C. Увеличить размер ответа
- D. Передавать идентификатор заказа только в URL

**Правильный ответ: B.** Ключ идемпотентности позволяет поставщику распознать повтор и вернуть результат первоначальной обработки вместо повторного создания заказа. Само добавление ключа без правил его хранения и повторного использования недостаточно.

### Вопрос 2

Что должен делать клиент, если API вернул ответ «заказ принят в обработку», но операция ещё не завершилась?

- A. Всегда сообщать пользователю, что заказ полностью создан
- B. Повторить запрос создания, пока не появится другой ответ
- C. Следовать контракту: показать состояние принятого запроса и использовать предусмотренный способ узнать результат
- D. Считать любой ответ успешным завершением

**Правильный ответ: C.** Принятие запроса не обязательно означает завершение операции. Контракт должен определить, как клиент получает итог: например, через идентификатор операции, отдельный запрос состояния или другой предусмотренный механизм.

### Вопрос 3

Какое изменение наиболее вероятно нарушит совместимость с существующими клиентами?

- A. Добавить необязательное поле в ответ
- B. Добавить новую независимую операцию
- C. Удалить поле, которое клиенты уже используют
- D. Добавить необязательный параметр, не меняя старое поведение

**Правильный ответ: C.** Удаление используемого поля может сломать потребителей. Даже, казалось бы, безопасное добавление поля требует учитывать клиентов, которые строго проверяют формат ответа, поэтому изменения следует проверять на реальных потребителях.

### Вопрос 4

Почему не следует безусловно повторять любой запрос после таймаута?

- A. Повтор всегда увеличивает размер ответа
- B. Запрос мог успешно выполниться, а потеряться мог только ответ; повтор способен создать дубль
- C. Таймаут означает, что сервер обработал запрос неправильно
- D. Повторы допустимы только для API, использующих XML

**Правильный ответ: B.** Таймаут не сообщает, завершилась ли операция на сервере. Для операций, меняющих состояние, нужны идемпотентность и явно определённая политика повторов.

## Практическое задание

Спроектируйте контракт API для оформления заказа в учебном интернет-магазине. Потребители — веб-сайт и мобильное приложение; поставщик — система заказов.

Подготовьте короткую спецификацию, включающую:

1. Операцию создания заказа: метод, путь и назначение.
2. Пример запроса и успешного ответа.
3. Минимум три бизнес-ошибки и две технические ошибки. Для каждой укажите, что может сделать клиент.
4. Поведение при таймауте и безопасном повторе запроса.
5. Правило идемпотентности: ключ, область действия и поведение при повторном запросе.
6. Указание, заказ уже создан или запрос только принят в обработку.
7. Одно изменение API, которое будет обратно совместимым, и одно потенциально несовместимое изменение.

**Критерии самопроверки:** контракт понятен без устных пояснений; потребитель может отличить ошибку данных от временного сбоя; неизвестный результат после таймаута не приводит автоматически к повторному созданию заказа; внутренние детали реализации не раскрываются.

## Полезные материалы

- **OpenAPI Specification** — формат описания HTTP API, запросов, ответов и схем данных.
- **RFC 9110: HTTP Semantics** — семантика методов и статусов HTTP.
- **RFC 9457: Problem Details for HTTP APIs** — стандартный формат описания HTTP-ошибок.
- **Google AIP-180: Backwards compatibility** — рекомендации по совместимости API.
- **Microsoft REST API Guidelines** — практические рекомендации по проектированию REST API.

На следующей главе курс переходит от синхронных контрактов к асинхронному взаимодействию: очередям, событиям и обработке сообщений.
