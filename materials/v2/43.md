# Часть 4. Глава 4.3 — Контейнерная платформа

## Цель главы

Научиться упаковывать приложение интернет-магазина в контейнеры, развёртывать его в Kubernetes и обеспечивать предсказуемую работу: корректные probe-проверки, управление конфигурацией и секретами, service discovery, ограничение ресурсов и автомасштабирование. Мы также определим, какие компоненты системы должны масштабироваться вместе, а какие — оставаться строго ограниченными.

**Контейнер** упаковывает приложение, его зависимости и конфигурацию запуска в переносимый образ. **Kubernetes** оркестрирует контейнеры: планирует их на узлах, перезапускает при сбоях, распределяет трафик и масштабирует количество экземпляров. [kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)

## 1. Контейнерный образ

Контейнерный образ должен быть минимальным, воспроизводимым и не содержать секретов. Для интернет-магазина разумно использовать multi-stage build: на первом этапе собирается приложение, на втором — формируется лёгкий runtime-образ.

```dockerfile
# Build stage
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# Runtime stage
FROM node:22-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/package.json ./

USER node
EXPOSE 8080
CMD ["node", "dist/main.js"]
```

### Правила образа

| Правило | Причина |
|---|---|
| Не хранить секреты в образе | Образ может быть скопирован или извлечён |
| Использовать non-root пользователя | Уменьшает последствия компрометации контейнера |
| Фиксировать версию базового образа | Обеспечивает воспроизводимость |
| Не включать build-инструменты в runtime | Уменьшает размер и поверхность атаки |
| Использовать `.dockerignore` | Исключает лишние файлы и секреты |
| Присваивать неизменяемый тег или digest | Позволяет точно знать, что развёрнуто |

### Антипаттерн: `latest`

Тег `latest` не гарантирует одну и ту же версию образа. Для production следует использовать версию сборки, commit SHA или digest:

```text
shop/orders:1.4.2
shop/orders:git-8f31c2d
shop/orders@sha256:...
```

## 2. Компоненты Kubernetes

Для интернет-магазина можно выделить следующие workload-компоненты:

| Компонент | Тип | Масштабирование | Особенности |
|---|---|---|---|
| Веб-приложение | Deployment | Horizontal | Stateless |
| Административное приложение | Deployment | Ограниченное | Доступ только для сотрудников |
| Фоновый обработчик заказов | Deployment | Horizontal | Потребляет очередь |
| Обработчик складских событий | Deployment | Ограниченное | Критичная согласованность |
| Планировщик отчётов | CronJob | По расписанию | Не должен нагружать primary БД |
| Миграции БД | Job | Однократно | Часть pipeline поставки |

### Deployment: веб-приложение

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-web
  labels:
    app: shop-web
    environment: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: shop-web
  template:
    metadata:
      labels:
        app: shop-web
    spec:
      containers:
        - name: web
          image: registry.example.com/shop/web:1.4.2
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: shop-web-config
          env:
            - name: DATABASE_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: shop-db-secret
                  key: password
          resources:
            requests:
              cpu: 250m
              memory: 512Mi
            limits:
              cpu: 1
              memory: 1Gi
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 15
          startupProbe:
            httpGet:
              path: /health/started
              port: 8080
            failureThreshold: 30
            periodSeconds: 5
```

## 3. Probe-проверки

**Probe** — периодическая диагностика контейнера, которую выполняет kubelet. Kubernetes использует probes, чтобы решать, когда отправлять трафик на Pod, когда считать его нездоровым и когда перезапускать. [kubernetes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)

| Probe | Вопрос | Действие при ошибке |
|---|---|---|
| Startup | Приложение завершило инициализацию? | Не запускать liveness/readiness до успешного старта |
| Readiness | Готов ли Pod принимать трафик? | Исключить Pod из Service endpoints |
| Liveness | Жив ли процесс и способен ли продолжать работу? | Перезапустить контейнер |

### Различие проверок

```text
Readiness:
- база данных недоступна;
- кэш прогревается;
- приложение временно не готово.
Результат: Pod исключается из балансировки, но не перезапускается.

Liveness:
- процесс завис;
- внутренний deadlock;
- приложение не отвечает.
Результат: контейнер перезапускается.

Startup:
- приложение долго инициализируется;
- миграции или прогрев кэша занимают время.
Результат: liveness и readiness не проверяются до завершения старта.
```

### Антипаттерн: readiness зависит от внешнего сервиса

Если readiness-проверка обращается к СБП, то недоступность платёжного провайдера выведет из балансировки все Pod веб-приложения. Это неверно: приложение может принимать заказы и сохранять их в статусе `PENDING_PAYMENT`.

Readiness должен проверять локальную готовность Pod и его критичные внутренние зависимости, а не доступность каждой внешней интеграции.

## 4. Service discovery

**Service discovery** позволяет компонентам находить друг друга по стабильному имени, не зная IP-адресов отдельных Pod. В Kubernetes Service предоставляет виртуальный IP и балансирует трафик между Pod с совпадающими label. [kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)

```yaml
apiVersion: v1
kind: Service
metadata:
  name: orders-service
spec:
  selector:
    app: orders-service
  ports:
    - name: http
      port: 80
      targetPort: 8080
```

Внутри кластера модуль склада может обращаться к модулю заказов по имени:

```text
http://orders-service.shop.svc.cluster.local
```

### DNS-имена

```text
<service>.<namespace>.svc.cluster.local

orders-service.shop.svc.cluster.local
inventory-service.shop.svc.cluster.local
payment-service.shop.svc.cluster.local
```

При масштабировании или перезапуске Pod их IP меняются, но имя Service остаётся стабильным.

## 5. Конфигурация и секреты

Конфигурацию следует разделять на несекретные параметры и секреты.

| Тип данных | Хранилище | Примеры |
|---|---|---|
| Несекретная конфигурация | ConfigMap | URL сервиса, уровень логирования, тайм-ауты |
| Секреты | Secret / secret manager | Пароль БД, API-ключ СБП, токен СДЭК |
| Конфигурация окружения | Отдельные ConfigMap по средам | dev, staging, production |
| Версия приложения | Image tag | `1.4.2`, commit SHA |

### ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: shop-web-config
data:
  ORDERS_SERVICE_URL: "http://orders-service:80"
  PAYMENT_TIMEOUT_MS: "800"
  LOG_LEVEL: "info"
```

### Secret

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: shop-db-secret
type: Opaque
stringData:
  username: shop_app
  password: "<managed-by-secret-manager>"
```

В реальной production-конфигурации секреты должны синхронизироваться из внешнего secret manager либо использовать механизм, предоставляемый платформой. Kubernetes Secret сам по себе не является полноценным решением для шифрования и аудита доступа.

## 6. Ресурсы и планирование

**Requests** — гарантированный объём ресурсов, который Kubernetes учитывает при размещении Pod. **Limits** — верхняя граница потребления. Корректные requests и limits позволяют планировщику размещать Pod предсказуемо и защищать узлы от исчерпания ресурсов. [docs.cloud.google](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/vertical-pod-autoscaling)

| Компонент | CPU request | Memory request | CPU limit | Memory limit |
|---|---:|---:|---:|---:|
| Веб-приложение | 250m | 512Mi | 1 | 1Gi |
| Модуль заказов | 500m | 1Gi | 2 | 2Gi |
| Обработчик склада | 500m | 1Gi | 1 | 2Gi |
| Отчёты | 250m | 512Mi | 1 | 1Gi |

### Правила

- Request должен отражать реальную рабочую нагрузку.
- Memory limit следует устанавливать осторожно: его превышение часто приводит к завершению Pod.
- Для критичных компонентов нужно предусматривать headroom.
- Нельзя размещать все replica одного критичного компонента на одном узле.
- Нужно использовать Pod anti-affinity или topology spread constraints.

## 7. Автомасштабирование

**Horizontal Pod Autoscaler (HPA)** изменяет количество Pod в Deployment в зависимости от метрик: например, загрузки CPU, памяти или пользовательских метрик очереди. [kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: shop-web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: shop-web
  minReplicas: 3
  maxReplicas: 12
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

### Стратегия для интернет-магазина

| Компонент | Min replicas | Max replicas | Метрика |
|---|---:|---:|---|
| Веб-приложение | 3 | 12 | CPU 70% |
| Модуль заказов | 2 | 8 | CPU 70% или длина очереди |
| Обработчик склада | 2 | 6 | Длина очереди |
| Отчёты | 1 | 3 | Длина очереди отчётов |

### Важное ограничение

HPA масштабирует приложение, но не устраняет узкое место в базе данных. Если 12 Pod одновременно обращаются к одной БД, пул соединений и блокировки могут стать ограничителем. Поэтому масштабирование приложения должно сопровождаться лимитами соединений, кэшем и разделением нагрузки.

## 8. Rolling update

**Rolling update** постепенно заменяет старые Pod новыми. Kubernetes контролирует, сколько Pod может быть недоступно и сколько новых может быть создано сверх желаемого количества. [kubernetes](https://kubernetes.io/docs/concepts/workloads/management/)

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
```

При `maxUnavailable: 0` и `maxSurge: 1` система сначала создаёт новый Pod, дожидается его готовности и только затем завершает один старый. Это снижает риск потери пропускной способности при релизе.

### Условия безопасного rolling update

- Readiness-проверка действительно отражает готовность.
- Новая версия совместима с текущей схемой данных.
- Миграции БД выполняются отдельно и обратно совместимы.
- Старая и новая версии могут работать одновременно.
- Ошибки новой версии обнаруживаются метриками и алертами.

A. Ничем

**Ответить**

**Правильный ответ: B.**

Readiness управляет включением Pod в Service endpoints, liveness — перезапуском контейнера при зависании. [kubernetes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)

**2. Почему не следует использовать readiness probe, зависящую от СБП?**

C. Потому что readiness должна проверять только CPU

**Ответить**

<details>
<summary>Показать правильный ответ</summary>
