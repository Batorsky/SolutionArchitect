# Часть 2. Глава 2.2 — Выбор архитектурного стиля

## Цель главы

Научиться выбирать архитектурный стиль не по моде, а по обоснованным критериям: размеру команды, зрелости предметной области, требованиям к согласованности, нагрузке, скорости поставки и эксплуатационным возможностям. Для интернет-магазина мы сравним модульный монолит, микросервисную архитектуру и слоистую архитектуру, а затем обоснуем выбор для первой версии.

**Архитектурный стиль** — набор принципов организации системы: как выделяются части, как они взаимодействуют, кто владеет данными и как система развёртывается. Выбор стиля определяет не только код, но и процессы разработки, тестирования, эксплуатации и развития команды.

## 1. Слоистая архитектура

**Слоистая архитектура** разделяет приложение на уровни с разными обязанностями. Классический вариант включает уровень представления, уровень бизнес-логики и уровень доступа к данным. Мартин Фаулер описывает слоистую организацию как базовый способ структурирования корпоративных приложений, при котором каждый уровень предоставляет сервисы вышележащему. [martinfowler](https://martinfowler.com/eaaCatalog/)

```text
Уровень представления
Веб-интерфейс, административный интерфейс

Уровень приложения
Сценарии использования: оформить заказ, зарезервировать товар

Уровень предметной области
Заказ, складская позиция, правила резервирования

Уровень доступа к данным
Репозитории, ORM, SQL
```

### Применение к интернет-магазину

| Слой | Ответственность | Пример |
|---|---|---|
| Представление | Взаимодействие с пользователем | Карточка товара, корзина, форма заказа |
| Приложение | Координация операций | Создание заказа и запрос резерва |
| Предметная область | Бизнес-правила | Инвариант «нельзя зарезервировать больше, чем доступно» |
| Доступ к данным | Сохранение и чтение данных | Репозиторий заказов и складских позиций |

### Преимущества и ограничения

| Плюсы | Минусы |
|---|---|
| Простая и понятная структура | При неправильном применении бизнес-логика «стекает» в контроллеры или SQL |
| Быстрый старт для небольших систем | Слои могут превращаться в формальность |
| Удобна для одного приложения и небольшой команды | Не решает вопрос границ предметной области |
| Легко найти стандартные практики | Изменение одной бизнес-возможности затрагивает все слои |

### Антипаттерн: слои вместо границ

Слоистая архитектура отвечает на вопрос «какие технические обязанности есть у кода», но не отвечает на вопрос «какие бизнес-возможности принадлежат какому контексту». Если каталог, заказы, склад и платежи перемешаны в одних таблицах и сервисах, слои не предотвращают хаос.

## 2. Модульный монолит

**Модульный монолит** — одно развёртываемое приложение, внутри которого выделены модули с ясными границами, собственными данными и публичными интерфейсами. Модули взаимодействуют только через контракты, а не через прямое обращение к внутренним таблицам или классам другого модуля.

```text
Одно приложение
├── Модуль «Каталог»
├── Модуль «Заказы»
├── Модуль «Складской учёт»
├── Модуль «Платежи»
├── Модуль «Доставка»
└── Модуль «Клиенты»
```

В отличие от обычного монолита, здесь границы не декларируются, а соблюдаются: модуль заказов не читает таблицы склада напрямую и не изменяет его данные в обход правил.

### Применение к интернет-магазину

| Модуль | Владеет | Публичный контракт |
|---|---|---|
| Каталог | Карточки, изображения, характеристики | Получить карточку товара |
| Заказы | Заказы, позиции, статусы | Создать заказ, подтвердить оплату, отменить заказ |
| Складской учёт | Остатки, резервы, движения | Зарезервировать, освободить резерв, списать |
| Платежи | Платежи и их статусы | Создать платёж, подтвердить платёж |
| Доставка | Способы доставки, отправления | Создать отправление, обновить статус |
| Клиенты | Профили и адреса | Получить данные покупателя |

### Почему это подходит первой версии

Для интернет-магазина модульный монолит даёт баланс между скоростью поставки и архитектурной дисциплиной:

- одна команда может развивать систему без координации нескольких сервисов;
- проще обеспечить строгую согласованность резерва и заказа;
- меньше сетевых вызовов и точек отказа;
- проще локальная разработка, отладка и тестирование;
- сохраняются границы контекстов, подготовленные в главе 2.1.

Модульный монолит особенно уместен, когда границы предметной области ещё уточняются, команда небольшая, а разные части системы не требуют радикально разного масштабирования. [fullscale](https://fullscale.io/blog/modular-monolith-vs-microservices/)

## 3. Микросервисная архитектура

**Микросервисная архитектура** разделяет систему на независимо развёртываемые сервисы, каждый из которых владеет своей предметной возможностью и данными. Сервисы взаимодействуют по сети через API или асинхронные сообщения. [learn.microsoft](https://learn.microsoft.com/en-us/azure/architecture/microservices/design/data-considerations)

```text
Сервис каталога ── API ── Сервис заказов ── API ── Сервис склада
       │                    │                      │
       └── своя БД          └── своя БД            └── своя БД
```

Ключевое правило: сервис владеет своими данными, а другие сервисы не обращаются к его хранилищу напрямую. Это ограничивает связанность и позволяет развивать сервисы независимо, но делает межсервисные бизнес-процессы распределёнными. [learn.microsoft](https://learn.microsoft.com/en-us/azure/architecture/microservices/design/data-considerations)

### Когда микросервисы оправданы

| Условие | Почему это важно |
|---|---|
| Несколько автономных команд | Команды могут выпускать изменения независимо |
| Разные профили нагрузки | Например, каталог и склад требуют разного масштабирования |
| Разные требования к доступности | Сбой одного сервиса не должен останавливать всю систему |
| Зрелые границы предметной области | Границы сервисов совпадают с устойчивыми контекстами |
| Зрелая DevOps-практика | Есть автоматизация развёртывания, мониторинга и эксплуатации |

### Цена микросервисов

| Плюсы | Минусы |
|---|---|
| Независимое развёртывание | Сетевые задержки и частичные отказы |
| Изоляция отказов | Распределённая согласованность |
| Независимое масштабирование | Сложнее отладка и наблюдаемость |
| Автономность команд | Выше требования к DevOps и инфраструктуре |
| Технологическая гибкость | Дублирование инфраструктуры и контрактов |

Для небольшой команды микросервисы часто добавляют операционную сложность раньше, чем приносят пользу от автономности. [ness](https://www.ness.com/blog/modular-monolith-vs-microservices/)

## 4. Сравнение стилей

| Критерий | Слоистый монолит | Модульный монолит | Микросервисы |
|---|---|---|---|
| Развёртывание | Одно приложение | Одно приложение | Много независимых сервисов |
| Границы | Технические слои | Бизнес-модули и контексты | Бизнес-возможности и данные |
| Владение данными | Обычно общая схема | Модули владеют своими таблицами или схемами | Каждый сервис владеет своими данными |
| Согласованность | Локальные транзакции | Локальные транзакции внутри модуля | Распределённая согласованность |
| Скорость первой поставки | Высокая | Высокая | Ниже |
| Эксплуатационная сложность | Низкая | Низкая или средняя | Высокая |
| Независимое масштабирование | Нет | Ограниченное | Да |
| Независимая поставка | Нет | Нет | Да |
| Подходит для | Небольшого приложения | Растущего продукта и небольшой команды | Нескольких автономных команд |

## 5. Критерии выбора для интернет-магазина

Применим критерии к текущей ситуации.

| Критерий | Фактическое условие | Вывод |
|---|---|---|
| Размер команды | Небольшая команда | Микросервисы преждевременны |
| Зрелость домена | Границы ещё уточняются: склады, доставка, резервы | Нужна возможность изменять модель |
| Нагрузка | Умеренная, один склад и один магазин | Нет потребности в независимом масштабировании |
| Согласованность | Критична для резервов и остатков | Проще обеспечить в одном приложении |
| Скорость поставки | Бизнес ждёт быстрого отказа от Excel | Модульный монолит ускоряет первую версию |
| Эксплуатация | Нет выделенной платформенной команды | Микросервисы увеличат операционную нагрузку |
| Будущее развитие | Новые склады, магазины, СДЭК | Нужны чёткие модульные границы |

**Решение:** для первой версии выбрать **модульный монолит** с контекстами каталога, заказов, складского учёта, платежей, доставки и клиентов.

Это не означает отказ от микросервисов навсегда. Это означает, что система начинается с дисциплинированных внутренних границ, которые при необходимости позволят выделить сервис позднее.

## 6. Когда выделять микросервис

Выделение сервиса оправдано, когда появляется конкретная причина, а не просто желание «сделать современно».

| Сигнал | Возможное решение |
|---|---|
| Складской модуль требует отдельного масштабирования из-за пиковой нагрузки | Выделить сервис складского учёта |
| Команда платежей должна выпускать изменения независимо | Выделить сервис платежей |
| Интеграция с несколькими службами доставки требует изоляции отказов | Выделить сервис доставки |
| Каталог должен выдерживать высокую читающую нагрузку | Выделить сервис каталога с собственной моделью хранения |
| Разные команды владеют разными бизнес-возможностями | Разделить владение по контекстам |

### Антипаттерн: сервис на каждую таблицу

Создание отдельного сервиса для каждой сущности — «сервис заказов», «сервис позиций заказа», «сервис статусов», «сервис адресов» — обычно приводит к чрезмерной распределённости. Такие сервисы не являются самостоятельными бизнес-возможностями и создают множество сетевых зависимостей без реальной автономии.

## 7. ADR-002: модульный монолит для первой версии

```text
# ADR-002: Реализовать первую версию как модульный монолит

Статус: Принято

## Контекст

Система управления продажами и заказами создаётся небольшой командой.
Требуется быстро автоматизировать заказы, складской учёт и резервирование.
Бизнес планирует новые магазины, склады и интеграцию с СДЭК,
но границы будущей модели ещё уточняются.

Критические требования:
- строгая согласованность резервов и остатков;
- быстрая поставка первой версии;
- низкая эксплуатационная сложность;
- возможность последующего выделения модулей.

## Рассмотренные варианты

1. Слоистый монолит без выраженных бизнес-границ.
2. Модульный монолит.
3. Микросервисная архитектура.

## Решение

Первая версия реализуется как модульный монолит.
Внутри одного приложения выделяются модули:
каталог, заказы, складской учёт, платежи, доставка и клиенты.

Модули взаимодействуют только через определённые интерфейсы.
Каждый модуль владеет своими данными и не изменяет данные
другого модуля напрямую.

## Последствия

Положительные:
- быстрее реализуется первая версия;
- проще обеспечить согласованность резервирования;
- ниже эксплуатационные затраты;
- сохраняется возможность выделения сервисов в будущем.

Отрицательные:
- все модули развёртываются вместе;
- масштабировать отдельную бизнес-возможность сложнее;
- требуется дисциплина, чтобы границы модулей не размывались.

Условия пересмотра:
- появление нескольких автономных команд;
- подтверждённая потребность в независимом масштабировании;
- необходимость изоляции отказов отдельного контура;
- существенное усложнение процесса сборки и поставки.
```

Слои структурируют код по техническим обязанностям: интерфейс, приложение, домен, данные. Границы предметной области задаются контекстами и модулями, а не уровнями. [martinfowler](https://martinfowler.com/eaaCatalog/)

</details>
