# Часть 3. Глава 3.7 — Проверка архитектуры

## Цель главы

Научиться проверять, что архитектура действительно соответствует бизнес-целям, атрибутам качества и ограничениям, а не только хорошо выглядит на диаграммах. Мы проведём облегчённую оценку по методу ATAM, определим архитектурные fitness functions, спланируем нагрузочные испытания и учения по отказоустойчивости для интернет-магазина.

**ATAM** (Architecture Tradeoff Analysis Method) — сценарно-ориентированный метод анализа архитектуры, который выявляет риски, чувствительные точки и компромиссы между атрибутами качества. Он предполагает анализ архитектурных подходов через приоритетные сценарии заинтересованных сторон. [apps.dtic](https://apps.dtic.mil/sti/tr/pdf/ADA413696.pdf)

## 1. Зачем проверять архитектуру

Архитектурное решение считается обоснованным не в момент его записи в ADR, а когда его последствия проверены. Для интернет-магазина необходимо ответить на вопросы:

- выдержит ли витрина пик распродажи;
- исключает ли система двойное резервирование последнего товара;
- сохранится ли заказ, если СБП временно недоступен;
- восстановится ли система в пределах RTO и RPO;
- можно ли добавить новый склад без переделки модели заказов;
- выявляются ли нарушения доступа и аномалии остатков.

Проверка архитектуры связывает требования, решения и фактическое поведение системы.

## 2. ATAM-lite

Полный ATAM подходит для крупных систем и требует значительного времени. Для первой версии интернет-магазина достаточно **ATAM-lite**: сокращённой сессии с фиксированным набором сценариев, архитектурных решений и рисков. [apps.dtic](https://apps.dtic.mil/sti/tr/pdf/ADA413696.pdf)

### Участники

| Роль | Задача |
|---|---|
| Владелец бизнеса | Подтвердить бизнес-цели и приоритеты |
| Продуктовый менеджер | Представить критические сценарии |
| Архитектор | Показать решения и компромиссы |
| Разработчики | Оценить реализуемость и риски |
| Эксплуатация / DevOps | Оценить наблюдаемость, восстановление и эксплуатацию |
| Представитель склада | Проверить реальность складских сценариев |
| Модератор | Фиксировать риски, решения и действия |

### Шаги ATAM-lite

```mermaid
flowchart LR
    A["Бизнес-цели<br/>и ограничения"] --> B["Приоритетные сценарии"]
    B --> C["Архитектурные решения"]
    C --> D["Анализ сценариев"]
    D --> E["Риски, чувствительные точки,<br/>компромиссы"]
    E --> F["План проверок<br/>и действий"]
```

| Шаг | Вопрос | Результат |
|---|---|---|
| 1 | Какие бизнес-цели критичны? | Автоматизация заказов, достоверные остатки, готовность к росту |
| 2 | Какие сценарии приоритетны? | Пик распродажи, двойное резервирование, сбой СБП |
| 3 | Какие решения их реализуют? | Модульный монолит, резервирование, outbox, bulkhead |
| 4 | Как решение ведёт себя при сценарии? | Анализ времени, отказов, согласованности |
| 5 | Где возникают риски? | Реестр рисков и чувствительных точек |
| 6 | Как проверить решение? | Нагрузочные тесты, chaos-учения, fitness functions |

## 3. Приоритетные сценарии

Для интернет-магазина выберем пять сценариев.

| ID | Сценарий | Атрибуты качества | Архитектурные решения |
|---|---|---|---|
| S-01 | Пик распродажи: 25 запросов/с на витрину | Производительность, доступность | Горизонтальное масштабирование, кэш, CDN |
| S-02 | Два покупателя заказывают последний экземпляр | Согласованность | Агрегат складской позиции, блокирующее резервирование |

## 4. Анализ сценария S-02

### Сценарий

```text
Два покупателя одновременно оформляют заказ
на последний экземпляр товара SKU-123.

Требование:
только один заказ может получить подтверждение.
```

### Архитектурный путь

```text
Веб-приложение
-> Модуль заказов
-> Складской контекст
-> Агрегат StockItem
-> Транзакционное резервирование
```

### Анализ

| Вопрос | Ответ |
|---|---|
| Где находится точка конфликта? | Обновление `reservedQuantity` в агрегате `StockItem` |
| Какая гарантия нужна? | Атомарность проверки и увеличения резерва |
| Что произойдёт при конкурентном доступе? | Одна операция успешна, вторая получает `409 Conflict` |
| Что будет при повторе запроса? | Идемпотентность по `reservationRequestId` |
| Что будет при сбое после резерва? | Резерв освобождается по истечении срока либо компенсацией |
| Как проверить? | Конкурентный интеграционный тест и нагрузочный тест |

### Результат анализа

```text
Риск:
Если резервирование выполняется вне транзакции складского агрегата,
возможно двойное резервирование.

Чувствительная точка:
Механизм блокировки или условного обновления
в агрегате StockItem.

Компромисс:
Строгая согласованность резерва ограничивает
параллельную пропускную способность складского контура.

Действие:
Добавить конкурентный тест и метрику
stock_reservation_conflicts_total.
```

## 5. Fitness functions

**Архитектурная fitness function** — автоматизированная проверка, которая оценивает, насколько реализация соответствует архитектурным характеристикам. Она превращает архитектурные правила из договорённостей в проверяемые ограничения.

| Характеристика | Fitness function | Способ проверки |
|---|---|---|
| Согласованность | Не допускается `availableQuantity < 0` | Тест инварианта и проверка данных |
| Модульность | Модуль заказов не обращается к таблицам склада | Статический анализ зависимостей |
| Производительность | p95 создания заказа не более 2 секунд | Нагрузочный тест |
| Контрактная совместимость | API не содержит несовместимых изменений | Сравнение OpenAPI-спецификаций |
| Безопасность | Нет секретов в коде и логах | SAST, secret scanning, проверка логов |
| Наблюдаемость | Критичный запрос содержит `traceId` | Интеграционный тест и проверка телеметрии |
| Восстанавливаемость | Восстановление из копии завершается в пределах RTO | Регулярное учение |

### Примеры правил

```text
Правило 1:
Модуль orders не может импортировать внутренние классы
модуля inventory.

Правило 2:
Изменение OpenAPI, удаляющее поле ответа,
блокирует merge без новой мажорной версии.

Правило 3:
Тест конкурентного резервирования
должен подтверждать ровно один успешный резерв.

Правило 4:
В логах запрещены поля password, cardNumber, apiKey.

Правило 5:
Восстановление из резервной копии
должно укладываться в RTO 2 часа.
```

## 6. Нагрузочные испытания

**Нагрузочное испытание** проверяет поведение системы при заданном профиле нагрузки. Его цель — не получить рекордное число запросов, а подтвердить или опровергнуть SLO.

### Сценарий: пик распродажи

```text
Профиль:
- 25 запросов/с к карточкам товаров;
- 5 запросов/с к поиску;
- 0,5 заказа/с;
- 0,5 операции резервирования/с;
- 0,25 платежа/с;
- длительность: 30 минут.

Целевые показатели:
- p95 карточки товара <= 1,5 с;
- p95 оформления заказа <= 2 с;
- error rate < 1%;
- отсутствие двойных резервирований;
- глубина очереди не растёт бесконечно.
```

### Этапы теста

1. Измерить базовую производительность без нагрузки.
2. Постепенно увеличивать нагрузку до расчётного пика.
3. Удерживать пик 30 минут.
4. Проверить p50, p95, p99, error rate и утилизацию ресурсов.
5. Проверить поведение после снижения нагрузки.
6. Зафиксировать узкое место.

### Что измерять

| Метрика | Цель |
|---|---|
| Throughput | Соответствие профилю нагрузки |
| Latency p95 и p99 | Не превышение SLO |
| Error rate | Менее 1% |
| DB connections | Нет исчерпания пула |
| Queue depth | Стабильность или контролируемый рост |
| Cache hit ratio | Достаточная эффективность кэша |
| Business invariants | Ноль двойных резервирований |

## 7. Учения по отказоустойчивости

**Chaos engineering** — практика controlled-воспроизведения реальных отказов для проверки того, как система реагирует на них. Перед экспериментом фиксируются гипотеза, метрики, критерии остановки и план отката. [learn.microsoft](https://learn.microsoft.com/en-us/power-platform/well-architected/reliability/testing-strategy)

### Эксперимент: недоступность СБП

```text
Гипотеза:
При недоступности СБП заказы сохраняются,
товары остаются в резерве до истечения срока,
покупатель получает понятное сообщение,
а система не создаёт дубликаты заказов.

Метрики:
- error rate оформления заказа;
- количество заказов в PENDING_PAYMENT;
- количество активных резервов;
- состояние circuit breaker;
- p95 времени ответа.

Действие:
Имитировать тайм-аут или 503 от СБП.

Крит!ерии успеха:
- заказ не теряется;
- нет двойного резерва;
- circuit breaker открывается;
- после восстановления оплата возможна;
- пользователь получает понятный ответ.

Критерий остановки:
- недоступность витрины;
- неконтролируемый рост ошибок;
- нарушение инвариантов остатков.
```

### Другие учения

| Эксперимент | Проверяемое свойство |
|---|---|
| Отключить кэш | Деградация витрины и нагрузка на БД |
| Задержать складской ответ | Тайм-ауты, retry, поведение пользователя |
| Потерять событие `PaymentConfirmed` | Outbox, повторная доставка, идемпотентность |
| Убить один экземпляр приложения | Балансировка и отсутствие потери заказов |
| Восстановить БД из копии | RTO и RPO |
| Заблокировать доступ к реплике | Переключение чтения и отчётов |

## 8. Отчёт по проверке архитектуры

```text
Отчёт ATAM-lite: интернет-магазин, первая версия

Бизнес-цели:

- достоверные остатки;
- готовность к нескольким складам и каналам.

S-04 потеря БД;
S-05 добавление склада.

Подтверждённые решения:
- модульный монолит;
- резервирование в складском агрегате;
- идемпотентные API;
- transactional outbox;
- кэш витрины;

R-04 непроверенное восстановление.

План проверок:
- конкурентный тест резервирования;
- нагрузочный тест пика;

```

## Вопросы для самопроверки

**1. Что выявляет ATAM?**

A. Только ошибки компиляции  
B. Риски, чувствительные точки и компромиссы архитектуры на основе сценариев  
C. Только уязвимости паролей  
D. Только стоимость облачных ресурсов

**Ответить**

<details>
<summary>Показать правильный ответ</summary>

**Правильный ответ: B.**

ATAM анализирует архитектурные подходы через приоритетные сценарии и выявляет риски, sensitivity points и tradeoff points. [apps.dtic](https://apps.dtic.mil/sti/tr/pdf/ADA413696.pdf)

</details>

***

**2. Что такое архитектурная fitness function?**

A. Ручной отчёт о прогрессе проекта

C. Способ расчёта стоимости облака  
D. Вид нагрузочного теста

**Ответить**

<details>
<summary>Показать правильный ответ</summary>

**Правильный ответ: B.**

Fitness function превращает архитектурное правило в проверяемое ограничение: например, тест инварианта остатков или статический анализ запрещённых зависимостей между модулями.
