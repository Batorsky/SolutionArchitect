# Часть 2. Глава 2.3 — Синхронные контракты и API

## Цель главы

Научиться проектировать синхронные контракты между частями системы: определять ресурсы, операции, коды ошибок, правила идемпотентности и версионирования. Мы применим это к интернет-магазину — к взаимодействию веб-приложения, модуля заказов, складского учёта и платёжного сервиса.

**API-контракт** — соглашение о том, какие операции предоставляет сервис, какие данные принимает и возвращает, какие ошибки возможны и как следует вести себя при повторных запросах. Хороший контракт делает интеграцию предсказуемой и позволяет развивать сервис без неожиданной поломки потребителей. [learn.microsoft](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-implementation)

## 1. Ресурсная модель API

В REST-подходе система моделируется через **ресурсы** — сущности или бизнес-понятия, к которым обращается клиент. Ресурс не обязан совпадать с таблицей базы данных: он отражает контракт, полезный потребителю. [learn.microsoft](https://learn.microsoft.com/en-us/azure/architecture/microservices/design/api-design)

Для интернет-магазина можно выделить такие ресурсы:

| Ресурс | Назначение | Пример |
|---|---|---|
| `products` | Карточки товаров для витрины | `GET /products/{productId}` |
| `orders` | Заказы покупателей | `POST /orders` |
| `orders/{orderId}` | Конкретный заказ | `GET /orders/{orderId}` |
| `orders/{orderId}/payment` | Платёж по заказу | `POST /orders/{orderId}/payment` |
| `stock-items` | Складские позиции | `GET /stock-items?sku=SKU-123` |
| `stock-items/{stockItemId}/reservations` | Резервы товара | `POST /stock-items/{stockItemId}/reservations` |
| `deliveries` | Отправления и доставка | `POST /deliveries` |

### Правило моделирования

Ресурс должен отражать **бизнес-понятие**, а не внутреннюю структуру таблицы.

Некорректно:

```http
POST /update_stock_table
POST /create_order_row
GET /get_data?table=orders
```

Корректно:

```http
POST /orders
GET /orders/{orderId}
POST /stock-items/{stockItemId}/reservations
```

## 2. Контракт модуля заказов

Модуль заказов предоставляет веб-приложению и административному интерфейсу операции жизненного цикла заказа.

### Создание заказа

```http
POST /v1/orders
Content-Type: application/json
Idempotency-Key: 7f3c9a2e-1b64-4f21-9d0e-5a2f6b8c1234

{
  "customerId": "cust-1024",
  "items": [
    {
      "productId": "prod-889",

      "quantity": 1
    }
  ],

```

## 3. Контракт складского учёта

Складской контекст владеет остатками и резервами. Модуль заказов не изменяет его данные напрямую, а вызывает определённые операции.

### Создание резерва

```http
POST /v1/stock-items/stock-771/reservations
Content-Type: application/json
Idempotency-Key: reservation-ord-50021-item-1

{
  "orderId": "ord-50021",
  "sku": "SKU-123",
  "quantity": 1,
  "expiresAt": "2026-11-01T19:45:00Z"
}
```

Успешный ответ:

```http
HTTP/1.1 201 Created
Location: /v1/stock-items/stock-771/reservations/res-90311

{
  "reservationId": "res-90311",
  "stockItemId": "stock-771",
  "orderId": "ord-50021",
  "sku": "SKU-123",
  "quantity": 1,
  "status": "ACTIVE",
  "expiresAt": "2026-11-01T19:45:00Z"
}
```

### Отказ при недостатке товара

```http
HTTP/1.1 409 Conflict

{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "Requested quantity is not available.",
    "details": {
      "sku": "SKU-123",
      "requestedQuantity": 1,
      "availableQuantity": 0
    }
  }
}
```

Код `409 Conflict` уместен, когда запрос корректен по формату, но противоречит текущему состоянию ресурса. [learn.microsoft](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-design)

## 4. Идемпотентность

**Идемпотентность** — свойство операции, при котором её повторное выполнение не приводит к дополнительному эффекту. Это критично для операций создания заказа, резервирования и проведения платежа: сеть может оборваться после того, как сервер уже обработал запрос, и клиент выполнит повтор. [learn.microsoft](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-implementation)

### Проблема без идемпотентности

```text
1. Клиент отправляет POST /orders.
2. Сервер создаёт заказ ord-50021.
3. Ответ не доходит из-за сбоя сети.
4. Клиент повторяет запрос.
5. Создаётся второй заказ ord-50022.
```

Для магазина это означает двойной резерв, двойное списание или двойную отправку.

### Решение: ключ идемпотентности

Клиент передаёт уникальный `Idempotency-Key`. Сервис сохраняет результат первой обработки и при повторе возвращает тот же результат, не создавая новый заказ.

```text
Первый запрос:
Idempotency-Key: 7f3c9a2e-...
Результат: создан заказ ord-50021.

Повторный запрос с тем же ключом:
Результат: возвращён существующий заказ ord-50021.
Новый заказ не создаётся.
```

### Какие операции должны быть идемпотентными

| Операция | Почему важна идемпотентность |
|---|---|
| Создание заказа | Повтор не должен создавать второй заказ |
| Резервирование товара | Повтор не должен уменьшать доступный остаток дважды |
| Подтверждение платежа | Повтор не должен списывать деньги или переводить заказ в оплату повторно |
| Отмена заказа | Повтор не должен вызывать повторное освобождение резерва |
| Передача на сборку | Повтор не должен создавать второе складское задание |

## 5. Управление ошибками

Ошибка должна быть понятной, безопасной и машиночитаемой. В production-ответе не следует возвращать стек-трейсы, внутренние сообщения исключений или детали реализации. [learn.microsoft](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-implementation)

### Единая структура ошибки

```json
{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "Requested quantity is not available.",
    "traceId": "b6f2e7a1-4f8c-4d19-9a2e-88b1c9d0f731",
    "details": {
      "sku": "SKU-123",
      "requestedQuantity": 1,
      "availableQuantity": 0
    }
  }
}
```

### Рекомендуемые коды

| Ситуация | Код | Пример |
|---|---|---|
| Некорректный запрос | `400 Bad Request` | Отрицательное количество товара |
| Нет доступа | `401 Unauthorized` | Отсутствует или недействителен токен |
| Доступ запрещён | `403 Forbidden` | Сотрудник пытается изменить чужой заказ |
| Ресурс не найден | `404 Not Found` | Несуществующий `orderId` |
| Конфликт состояния | `409 Conflict` | Товар уже зарезервирован другим покупателем |
| Нарушена валидация | `422 Unprocessable Entity` | Заказ без позиций |
| Внутренняя ошибка | `500 Internal Server Error` | Сбой базы данных |
| Сервис временно недоступен | `503 Service Unavailable` | Платёжный провайдер недоступен |

### Ошибки предметной области

Не каждую бизнес-ошибку следует превращать в `500`. Если система корректно определила, что товар закончился, это не внутренняя ошибка сервера, а ожидаемый конфликт состояния.

```text
Некорректно:
500 Internal Server Error
"Reservation failed"

Корректно:
409 Conflict
"INSUFFICIENT_STOCK"
```

## 6. Версионирование интерфейсов

**Версионирование** позволяет изменять контракт, не ломая существующих потребителей. Обратная совместимость означает, что старый клиент продолжает работать после обновления сервиса. [learn.microsoft](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-implementation)

### Что является совместимым изменением

| Изменение | Совместимость |
|---|---|
| Добавить необязательное поле в ответ | Обычно совместимо |
| Добавить новый endpoint | Обычно совместимо |
| Добавить необязательный параметр запроса | Обычно совместимо |
| Переименовать поле | Несовместимо |
| Удалить поле | Несовместимо |
| Изменить тип поля | Несовместимо |
| Сделать необязательное поле обязательным | Несовместимо |
| Изменить смысл кода ошибки | Несовместимо |

### Стратегии версионирования

| Стратегия | Пример | Плюсы | Минусы |
|---|---|---|---|
| Версия в URI | `/v1/orders` | Простая маршрутизация и читаемость | Дублирование путей |
| Версия в заголовке | `Accept: application/vnd.shop.v2+json` | Чистые URI | Сложнее отладка и кэширование |
| Версия в параметре | `/orders?version=2` | Простота реализации | Может смешиваться с бизнес-параметрами |

Для первой версии интернет-магазина практичен вариант с версией в URI:

```http
GET /v1/orders/ord-50021
POST /v1/orders
```

При несовместимом изменении создаётся `/v2/orders`, а `/v1/orders` поддерживается в течение согласованного периода. [learn.microsoft](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-implementation)

## 7. Контракт платежей

Платёжный модуль скрывает детали СБП за собственным контрактом. Это позволит позже добавить другие способы оплаты без изменения модели заказа.

### Создание платежа

```http
POST /v1/payments
Content-Type: application/json
Idempotency-Key: payment-ord-50021

{
  "orderId": "ord-50021",
  "amount": 4590.00,
  "currency": "RUB",
  "method": "SBP"
}
```

```http
HTTP/1.1 201 Created

{
  "paymentId": "pay-70114",
  "orderId": "ord-50021",
  "status": "PENDING",
  "paymentUrl": "https://pay.example/sbp/session/abc123"
}
```

### Подтверждение платежа

```http
POST /v1/payments/pay-70114/confirmation
Idempotency-Key: confirm-pay-70114
```

```http
HTTP/1.1 200 OK

{
  "paymentId": "pay-70114",
  "orderId": "ord-50021",
  "status": "CONFIRMED"
}
```

После подтверждения модуль платежей уведомляет модуль заказов о событии `PaymentConfirmed`. Заказ переходит из статуса `PENDING_PAYMENT` в `CONFIRMED`, а резерв преобразуется в списание.

## 8. Антипаттерны API

### Удалённый вызов процедур

Если API состоит из операций вида `createOrderRecord`, `updateStockTable`, `recalculateOrder`, он отражает внутреннюю реализацию, а не бизнес-ресурсы. Такой контракт хрупок и затрудняет развитие.

### Несогласованные ошибки

Если один endpoint возвращает `400`, другой — `200` с полем `"error": true`, а третий — `500` при законном конфликте, потребители не могут надёжно обрабатывать ответы.

### Преждевременное версионирование

Создавать новую версию API для каждого небольшого изменения избыточно. Версия нужна для несовместимых изменений; совместимые расширения можно вводить без смены основной версии. [learn.microsoft](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-implementation)

### Отсутствие идемпотентности

Особенно опасно для платежей и резервирования. Повтор запроса при сбое сети может привести к финансовым или складским ошибкам.

A. Операция, которая всегда возвращает ошибку  
B. Операция, повторное выполнение которой не создаёт дополнительного эффекта  
C. Операция, которая выполняется только один раз технически  
D. Операция, доступная только администратору

**Ответить**

<details>
<summary>Показать правильный ответ</summary>

**Правильный ответ: B.**

Идемпотентность позволяет безопасно повторять запрос после сетевого сбоя или тайм-аута. Например, повторное создание заказа с тем же `Idempotency-Key` не должно создавать второй заказ. [learn.microsoft](https://learn.microsoft.com/en-us/azure/architecture/best-practices/api-implementation)
