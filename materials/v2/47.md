# Часть 4. Глава 4.7 — FinOps и эффективность ресурсов

## Цель главы

Научиться связывать архитектурные решения интернет-магазина с их стоимостью. Мы рассмотрим модель совокупной стоимости владения, распределение затрат по командам и бизнес-функциям, правайзинг, управление storage и network costs, а также механизмы, предотвращающие неконтролируемый рост облачных расходов.

**FinOps** — практика управления облачными затратами, объединяющая инженеров, продукт и финансы. Её цель — не минимизировать расходы любой ценой, а обеспечивать максимальную бизнес-ценность при контролируемой стоимости. Базовый цикл FinOps включает фазы **Inform**, **Optimize** и **Operate**. [finops](https://www.finops.org/framework/phases/)

## 1. Стоимость как архитектурное ограничение

Стоимость — не только финансовая метрика, но и архитектурное ограничение. Решение о managed PostgreSQL, числе реплик, CDN, очередях и уровне резервирования должно опираться на соотношение ценности, риска и затрат.

| Решение | Архитектурный эффект | Финансовый эффект |
|---|---|---|
| Multi-AZ database | Выше доступность | Выше стоимость |
| Read replica | Разгрузка основной БД | Дополнительный экземпляр |
| CDN | Ниже latency, меньше нагрузка на origin | Стоимость трафика и запросов |
| Autoscaling | Соответствие мощности нагрузке | Оплата по фактическому потреблению |
| Долгосрочные обязательства | Предсказуемая базовая мощность | Скидка, но обязательство |
| Избыточные реплики | Потенциально выше надёжность | Пустая мощность и лишние расходы |

### Антипаттерн: оптимизация без SLO

Если снижать размер базы данных или число реплик без измерения latency, error rate и бизнес-метрик, экономия может обернуться нарушением SLO и потерей заказов. Cost optimization всегда должен начинаться с целевых уровней надёжности и производительности.

## 2. Модель совокупной стоимости

**TCO** (Total Cost of Ownership) учитывает не только счёт облачного провайдера, но и затраты на разработку, эксплуатацию, поддержку, обучение, инциденты и миграцию.

```text
TCO =
  cloud infrastructure
+ licenses
+ engineering and operations
+ support and maintenance
+ observability and security tooling
+ incident and downtime cost
+ migration and training cost
```

### Компоненты для интернет-магазина

| Категория | Примеры затрат |
|---|---|
| Compute | Виртуальные машины, Kubernetes nodes, FaaS |
| Data | Managed PostgreSQL, кэш, очереди, аналитическое хранилище |
| Storage | Object storage, резервные копии, логи, метрики |
| Network | Egress, NAT, private endpoints, CDN |
| Security | WAF, secrets, scanning, identity |
| Observability | Логи, метрики, трейсы, алертинг |
| Engineering | Разработка, тестирование, эксплуатация, миграции |

## 3. Фазы FinOps

| Фаза | Вопрос | Действия |
|---|---|---|
| Inform | «На что и кем расходуются ресурсы?» | Теги, allocation, dashboards, showback |
| Optimize | «Где можно повысить эффективность?» | Rightsizing, autoscaling, storage tiering, устранение idle-ресурсов |
| Operate | «Как удерживать результат?» | Политики, бюджеты, алерты, регулярные обзоры |

FinOps-модель предполагает точное распределение расходов по командам, продуктам и бизнес-единицам, а затем регулярный анализ и внедрение оптимизаций. [finops](https://www.finops.org/framework/phases/)

## 4. Теги и распределение затрат

Без обязательных тегов невозможно ответить, сколько стоит витрина, модуль заказов или склад. Теги должны быть частью IaC и pipeline, а не ручной практикой после создания ресурса. [finops](https://www.finops.org/framework/technology-categories/public-cloud/)

### Обязательные теги

```yaml
tags:
  application: shop-platform
  component: orders-service
  environment: production
  owner: ecommerce-platform-team
  cost-center: ecommerce
  business-function: order-management
  data-classification: confidential
```

### Модель распределения

| Ресурс | Модель затрат |
|---|---|
| Orders service | Прямая аллокация по тегу `component` |
| Managed PostgreSQL | Распределение по потреблению или фиксированная доля между заказами и складом |
| Shared network | Showback по бизнес-функциям |
| Observability | Распределение по объёму логов и метрик |
| CDN | По доменам и типам контента |

### Showback и chargeback

**Showback** показывает команде её фактические расходы, но не списывает их из бюджета команды. **Chargeback** переносит затраты на ответственное подразделение. [finops](https://www.finops.org/framework/technology-categories/public-cloud/)

Для первого этапа обычно достаточно showback: он формирует ответственность без бюрократизации.

## 5. Rightsizing

**Rightsizing** — подбор размера ресурса по фактической нагрузке, а не по консервативной оценке. Это относится к виртуальным машинам, Kubernetes nodes, managed databases, кэшам и storage. [finops](https://www.finops.org/framework/phases/)

```text
Было:
Kubernetes node: 16 vCPU / 64 GB
Средняя загрузка: 18% CPU, 25% memory

Стало:
Kubernetes node: 8 vCPU / 32 GB
Средняя загрузка: 36% CPU, 50% memory
```

### Правила

- Анализировать p50, p95 и p99, а не только среднее.
- Учитывать пики: распродажи, акции, сезонность.
- Не уменьшать ресурсы ниже SLO.
- Проверять влияние на latency, error rate и очереди.
- Менять размер постепенно и с наблюдаемостью.
- Автоматизировать рекомендации, но утверждать критичные изменения.

## 6. Autoscaling и базовая мощность

**Autoscaling** подстраивает количество экземпляров под нагрузку. Он эффективен для переменной части трафика, но не заменяет планирование базовой мощности. [avepoint](https://www.avepoint.com/topics/cloud-cost-optimization)

```mermaid
flowchart LR
    Metrics["Метрики: RPS, CPU, queue depth"] --> HPA["Autoscaler"]
    HPA --> Pods["Pods веб-приложения"]
    Pods --> Load["Нагрузка"]

    Load --> Metrics
```

### Модель мощности

```text
Базовая мощность:
- покрывает обычный дневной трафик;
- может резервироваться на длительный срок.

Пиковая мощность:
- создаётся autoscaling;
- оплачивается по потреблению.

Плановые пики:
- распродажи, кампании, сезонность;
- заранее увеличивают min replicas и capacity.
```

## 7. Управление storage costs

Хранилище часто растёт незаметно: логи, метрики, трейсы, резервные копии, дубли изображений и экспортированные отчёты. Управление жизненным циклом данных снижает затраты без потери нужной функциональности. [spot.rackspace](https://spot.rackspace.com/blog/cloud-cost-optimization)

| Тип данных | Политика |
|---|---|
| Изображения товаров | Хранить постоянно, версионировать, кэшировать в CDN |
| Логи приложения | 14–30 дней hot, затем archive или удаление |
| Метрики | Высокое разрешение — 14–30 дней, агрегаты — дольше |
| Трейсы | 7–14 дней, выборочное хранение |
| Резервные копии | Ежедневные — 30 дней, ежемесячные — 12 месяцев |
| Временные экспорты | Удаление через 1–7 дней |
| Архивные документы | Перевод в cold tier после заданного срока |

### Lifecycle-правило

```text
Object storage:
products/*           -> standard tier
logs/*               -> standard 14 дней -> archive 90 дней -> delete
exports/*            -> standard 3 дня -> delete
backups/daily/*      -> standard 30 дней -> delete
backups/monthly/*    -> archive 12 месяцев -> delete
```

## 8. Управление network costs

Наиболее непредсказуемые расходы часто связаны не с compute, а с сетью: egress, NAT, межзоновый трафик, повторные запросы к origin и неэффективные private endpoints.

| Источник затрат | Мера |
|---|---|
| Egress в интернет | CDN, кэширование, сжатие, ограничение внешних вызовов |
| NAT gateway | Private endpoints для managed services |
| Межзоновый трафик | Осознанное размещение stateful-компонентов |
| Повторные origin-запросы | Правильный cache TTL и versioning |
| Логи и метрики | Сэмплирование, агрегация, retention |
| Неиспользуемые endpoints | Регулярная инвентаризация |

### Пример

Если каждое изображение товара запрашивается из origin вместо CDN, растут расходы на compute, network и storage requests. Версионированные URL и длинный TTL для неизменяемых файлов снижают повторные обращения. [avepoint](https://www.avepoint.com/topics/cloud-cost-optimization)

## 9. Управление и контроль

Cost governance должна быть встроена в процесс поставки, а не выполняться раз в квартал.

| Механизм | Назначение |
|---|---|
| Обязательные теги в IaC | Гарантия аллокации затрат |
| Budget alerts | Раннее предупреждение о превышении |
| Cost anomaly detection | Обнаружение резких отклонений |
| Policy as code | Запрет незатегированных или избыточных ресурсов |
| Monthly FinOps review | Обзор затрат, аномалий и оптимизаций |
| Ownership model | У каждой стоимости есть ответственный |
| Forecast | Планирование бюджета на основе трендов |

FinOps-практики рекомендуют автоматизировать проверку тегов, отслеживать аномалии и регулярно проводить совместные обзоры затрат с инженерными и продуктовыми командами. [finops](https://www.finops.org/framework/phases/)

## 10. ADR-007: FinOps-политика интернет-магазина

```text
# ADR-007: Внедрить FinOps-политику для интернет-магазина

Статус: Принято

## Контекст

Система интернет-магазина использует managed services,
Kubernetes, CDN, object storage и observability.
Без единой модели аллокации и контроля невозможно
определить стоимость бизнес-функций и предотвратить
неконтролируемый рост расходов.

## Решение

1. Все ресурсы создаются через IaC и получают
   обязательные теги:
   application, component, environment, owner,
   cost-center, business-function, data-classification.

2. Pipeline блокирует создание незатегированных ресурсов.

3. Внедряется showback по компонентам и бизнес-функциям.

4. Для production устанавливаются бюджеты и cost alerts.

5. Rightsizing выполняется на основе p95/p99,
   бизнес-метрик и SLO, а не только среднего потребления.

6. Настраиваются lifecycle-политики для логов, метрик,
   резервных копий и временных файлов.

7. Managed services подключаются через private endpoints,
   чтобы снизить NAT и egress costs.

8. Ежемесячно проводится FinOps review:
   затраты, аномалии, прогноз, праваайзинг, обязательства.

## Последствия

Положительные:
- прозрачная стоимость бизнес-функций;
- ранняя диагностика аномалий;
- снижение waste;
- обоснованные архитектурные решения;
- предсказуемый бюджет.

Отрицательные:
- требуется дисциплина тегирования;
- добавляются задачи эксплуатации FinOps;
- необходимы инструменты отчётности;
- часть оптимизаций требует изменения архитектуры.

Условия пересмотра:
- существенное изменение модели ценообразования провайдера;
- появление новых крупных нагрузок;
- изменение структуры команд или бизнес-функций.
```
