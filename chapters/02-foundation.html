Из чего состоит современная система

Сначала — путь запроса

Представьте, что пользователь оформляет заказ. Приложение должно принять действие, проверить данные, сохранить заказ, передать информацию другим частям системы и показать результат.

Это не обязательно делает один компонент. Запрос может пройти через клиент, сеть, серверное приложение, базу данных и другие сервисы. Архитектору важно понимать обязанности этих частей и то, как они взаимодействуют.

Полезный вопрос: что происходит после того, как пользователь нажал кнопку, и какие компоненты участвуют в этом процессе?

Клиент и сервер

Клиент — часть системы, которая обращается за данными или услугой. Это может быть браузер, мобильное приложение или другой сервер.

Сервер принимает запросы, выполняет прикладную логику и возвращает результат. Он может обращаться к базе данных, кешу или другим системам.

Клиент и сервер — роли в конкретном взаимодействии, а не обязательно два отдельных физических компьютера. Один сервер может быть клиентом другого сервиса, когда вызывает его API.

Клиент

Показывает интерфейс, собирает действия пользователя и отправляет запросы.

Сервер

Проверяет запрос, выполняет бизнес-логику и формирует ответ.

API — договор между компонентами

API описывает, как одна часть системы может обратиться к другой: какие операции доступны, какие данные нужно передать и какие ответы или ошибки можно получить.

Например, операция создания заказа может принимать идентификатор товара и количество, а в ответ возвращать номер заказа и его статус. Хороший контракт понятен обеим сторонам и меняется согласованно.

При проектировании API важно заранее продумать проверку входных данных, обработку ошибок, аутентификацию, версионирование и то, что клиенту действительно нужно получить в ответ.

API — это не только адрес запроса. Это соглашение о поведении: формате данных, правилах и возможных результатах.

База данных — долговременное хранение

База данных хранит информацию, которая должна пережить завершение запроса и перезапуск приложения: учётные записи, заказы, платежи, настройки.

Выбор базы данных зависит от характера данных и способов работы с ними. Важно понять, какие запросы нужны системе, как связаны сущности, какие требования предъявляются к целостности и насколько быстро данные должны быть доступны.

Архитектору полезно уточнить: какие данные считаются источником истины, кто может их изменять, как долго их хранить и что делать при сбое или ошибочном изменении.

Кеш — быстрее, но сложнее

Кеш хранит копию данных, чтобы часто запрашиваемый результат можно было получить быстрее или без обращения к более медленному источнику. Это может снизить задержку и нагрузку на базу данных.

Но копия может устареть. Поэтому нужно решить, сколько она живёт, когда обновляется и допустимо ли временно показать не самые свежие данные.

Кеш особенно полезен, если данные часто читают, а меняются они относительно редко. Он не заменяет базу данных и не должен становиться единственным местом хранения важных данных без отдельного архитектурного обоснования.

Очереди — работа не обязательно сразу

Очередь сообщений позволяет одному компоненту передать работу другому, не ожидая, пока тот закончит. Например, после оформления заказа система может поставить задачу на отправку письма в очередь.

Основной запрос тогда может завершиться быстрее, а отправкой письма займётся отдельный обработчик. Очереди также помогают сгладить временные всплески нагрузки.

За это приходится платить сложностью: обработка может произойти позже, сообщения могут прийти повторно, а ошибки нужно отслеживать и обрабатывать. Нужно определить, какие операции можно выполнять асинхронно, а какие должны завершиться до ответа пользователю.

Сеть и задержки

Компоненты распределённой системы общаются по сети. Такой вызов может задержаться или завершиться ошибкой: например, сервис недоступен, соединение прервано или ответ пришёл слишком поздно.

Поэтому при проектировании взаимодействий учитывают время ожидания, повторные попытки, ограничения числа запросов и поведение при недоступности зависимого компонента. Повторять запрос бесконечно нельзя: это может усилить нагрузку и ухудшить ситуацию.

Чем больше сетевых взаимодействий требуется для одного действия, тем больше потенциальных задержек и точек отказа. Это одна из причин, почему архитектуру оценивают по реальным сценариям, а не только по диаграмме компонентов.

Проверь себя

Выбери один ответ в каждом вопросе, затем нажми «Проверить».

1. Для чего обычно используют API?

2. В чём важный компромисс при использовании кеша?

3. Что даёт очередь сообщений?

4. Как следует проектировать сетевой вызов к другому сервису?

Практическое задание

Возьмите сервис из паспорта, который вы подготовили в первой главе, и опишите путь одного типичного действия пользователя.

  1. Кто выступает клиентом и какой запрос он отправляет?
  2. Какой сервер или компонент принимает запрос?
  3. Какие данные нужно прочитать или сохранить?
  4. Есть ли смысл использовать кеш или очередь? Объясните почему.
  5. Что произойдёт, если база данных или внешний сервис временно недоступны?

Нарисуйте простую схему из блоков и стрелок. Не добавляйте компоненты «на будущее» без объяснения: для каждого блока укажите его задачу.

Полезные материалы

  • Обзор HTTP — MDN — клиент-серверная модель, запросы и ответы, а также роль компонентов между клиентом и сервером.
  • Что такое OpenAPI — как описывать HTTP API и использовать его спецификацию как общий контракт.
  • HTTP-кэширование — MDN — зачем кэшируют ответы и какие задачи кэширование помогает решать.
  • Введение в транзакции — PostgreSQL — базовое представление о транзакциях и группировке операций с данными.
  • RabbitMQ: «Hello World!» — простой пример отправки сообщения производителем и его получения потребителем.
